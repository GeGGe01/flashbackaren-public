## Verdict

Idea → an unusually coherent prototype core. The win isn't feature count — it's that the code
already preserves the load-bearing separations: Flashback UID ≠ username, activity ≠ quality,
direct ≠ rich rating, local identity ≠ person, upstream data ≠ our own user data. And
"over-engineering" has become the product's **differentiator** (genealogy, arbitrary weights,
absurd criteria, auditable computation) rather than a joke on top — a stronger idea than the
original "like users instead of posts."

**Brytpunkt:** the current inline HTML/CSS/JS front is right as the v1-core skeleton but wrong as
the base for the next product phase. It has done its job; the next phase needs real product surfaces.

## Changes before building more

- **Reputation presentation.** The maths (R = community + activity) is right, but community is
  *human judgement* and activity is *our mechanical modifier* — different epistemic status. The
  profile must let the user decompose R at a glance (community ★ + N ratings; activity +x; ── ; R),
  not bury it in a small line.
- **Rich rating "ej bedömd" (P0).** Four sliders starting at 0 means "I judged Humor and gave zero."
  The design means "I needn't judge irrelevant criteria." **0 ≠ unrated.** Each criterion starts
  *unrated*; only activated criteria enter the weighted mean. **[direktor]** invariant: the weighted
  mean is over ACTIVE criteria only, and a rich rating needs ≥1 active criterion.
- **Weights too narrow.** 1–5 is fine for the skeleton, but the design wants arbitrary weighting
  (e.g. Kunskap 73% / Humor 2% / Personlig vendetta 25%). Next schema: store weight as a
  non-negative number; UI offers presets AND exact weighting.
- **Templates: data → products (P0 freeze).** `templates(id,name,kind,created_at)` is enough for the
  Standard template, not the ecosystem. **Freeze the domain model in ONE migration** (not
  incremental ALTERs) with: template, template_version, criterion, template_criterion,
  parent_version, root_template, author_identity, visibility/tier, canonical_hash. Key:
  **template identity ≠ template version** ("Forumdebattör" is a work; "…v3" is an immutable
  version); a fork points at the exact version it forked from; **criteria get stable identity** so
  "Kunskap" survives a rename to "Ämneskunskap".
- **Atomic rich-rating write (P0 bug).** The rich write isn't atomic: upsert `ratings`, then delete
  old `rating_criteria`, then insert new ones one-by-one. A mid-way failure desyncs the overall
  score from its breakdown. **[direktor]** fix: one atomic unit via D1 `batch()`. Do this before any
  more rich-rating work — "show the calculation" depends on the two being consistent.
- **Doc drift.** README still says synthetic-only / live-lookup-deferred, but the code preseeds real
  members and resolves on miss. Fixed in this pass.
- **Member search scaling.** `LIKE '%q%'` is fine for hundreds; at tens/hundreds of thousands we need
  a separate search representation/index. Not now — but the model must not pretend `username` is both
  canonical presentation and optimal search field.
- **Front → React/Vite for the next phase (P1).** The surfaces below justify it (stateful views,
  reusable criterion controls, template editors, visualisations, navigation) — start from information
  architecture, not pixel polish.

## Next-phase surfaces (IA)

```text
Search → Member profile → { Reputation · Rating profile · Random review · Rate the user → pick template → direct/rich editor }
Templates → { Standard · Featured · Community } → Template profile → { use · configure · fork · genealogy }
```

Homepage: search-dominant ("look someone up on Flashbackaren", not a product pitch). Member profile:
lean HARD into old-forum feel — tables/panels, information density, less "app card"; the absurdly
advanced functionality should feel like it landed inside old forum software (that's the punchline,
stronger than a modern dashboard with Flashback colours). E.g. the radar plot sits under a drab grey
"Detaljerad bedömningsanalys" header, then shows an unreasonably competent visualisation.

Random review as a product feature (not a SQL detail): profile shows "Slumpmässigt omdöme" + exactly
one review, with [Visa ett annat] [Visa alla N].

## Priorities

- **P0:** (1) "ej bedömd" as a real criterion state; (2) freeze template/version/criterion domain
  model before building the ecosystem; (3) atomic rich-rating write.
- **P1:** React/Vite next front (IA first); profile as the central page decomposing
  community/activity/reputation; template discovery Standard→Featured→Community from v1 of the
  library (hard to repair after community data grows).
- **P2:** "show the calculation", random review, criterion visualisations; then verification /
  meta-user UI (mechanism matters but must not block the reputation product feeling right).

**[direktor] sequencing:** do the three P0s first — atomic write (quick bug), "ej bedömd" (model
correctness), then the domain-model freeze (design, supersedes the lighter V2 design in the
template-ecosystem contract) — before any ecosystem code. Verification/fingerprinting stay decoupled.
